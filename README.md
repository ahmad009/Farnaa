# ثبت سفارش فروشگاه

ثبت سفارش فروشگاه با .NET 8، EF Core 8 و SQL Server. موجودی هر فروشنده جداست و اگه ثبت سفارش شکست بخوره، موجودی رزروشده برمی‌گرده.

## اجرا

سولوشن با Visual Studio 2022 نسخهٔ 17.14 سازگاره. فایل `Marketplace.sln` رو باز کن، پروژهٔ `Marketplace.Api` رو به‌عنوان Startup Project انتخاب کن و `F5` بزن. صفحهٔ Swagger روی آدرس زیر باز می‌شه:

[Swagger](http://localhost:5080/swagger)

برای اجرای خط فرمان:

```powershell
dotnet restore Marketplace.sln
dotnet run --project src/Host/Marketplace.Api
```

نسخهٔ هدف برنامه .NET 8 هست. برای ساخت، `global.json` از SDK 9.0.3xx استفاده می‌کنه که با Visual Studio 2022 نسخهٔ 17.14 سازگاره. SQL Server هم باید نسخهٔ 2019 یا جدیدتر باشه.

دو اتصال `CatalogDb` و `OrderingDb` توی تنظیمات تعریف شدن. حالت پیش‌فرض، اتصال ویندوز به سرور محلی `.` هست. برای اتصال با حساب SQL، Connection Stringها رو توی User Secrets با شناسهٔ `Farnaa-Marketplace-Development` یا متغیرهای محیطی `ConnectionStrings__CatalogDb` و `ConnectionStrings__OrderingDb` بذار. رمز رو داخل فایل‌های پروژه ننویس.

## پابلیش

برای گرفتن خروجی قابل اجرا از Visual Studio:

1. روی پروژهٔ `Marketplace.Api` راست‌کلیک کن و `Publish` رو بزن.
2. گزینهٔ `Folder` رو انتخاب کن و یه پوشه برای خروجی بده.
3. تنظیمات رو روی `Release` بذار و `Publish` رو بزن.

همین کار از خط فرمان هم انجام می‌شه:

```powershell
dotnet publish src/Host/Marketplace.Api -c Release -o ./publish
```

بعد از داخل پوشهٔ خروجی این دستور رو اجرا کن:

```powershell
dotnet Marketplace.Api.dll --urls http://localhost:5080
```

با این روش برنامه به‌صورت پیش‌فرض در محیط `Production` اجرا می‌شه و Swagger نمایش داده نمی‌شه. حساب اتصال باید مجوز اعمال Migrationها رو داشته باشه؛ یا قبل از اجرا، اسکریپت‌های پوشهٔ `database` رو روی سرور مقصد اجرا کن.

## دیتابیس و دادهٔ اولیه

برنامه موقع شروع، Migrationهای هر دو دیتابیس رو اعمال می‌کنه. برای ساخت دستی، فایل‌های پوشهٔ `database` رو به‌ترتیب اجرا کن:

- `00-create-databases.sql`: ساخت دو دیتابیس، اگه از قبل وجود نداشته باشن.
- `01-catalog-migrations.sql`: ساخت جدول‌ها، ایندکس‌ها و داده‌های اولیهٔ Catalog؛ روی `CatalogDb` اجرا بشه.
- `02-ordering-migrations.sql`: ساخت جدول‌ها و ایندکس‌های Ordering؛ روی `OrderingDb` اجرا بشه.
- `03-seed-catalog.sql`: درج داده‌های نمونه با اسم‌های جدید، فقط اگه از قبل وجود نداشته باشن.


## ثبت سفارش

توی Swagger، مسیر `POST /api/orders` رو باز کن و `Try it out` رو بزن. می‌تونی با این درخواست شروع کنی:

```json
{
  "customerId": "40000000-0000-0000-0000-000000000001",
  "items": [
    {
      "sellingOptionId": "30000000-0000-0000-0000-000000000001",
      "quantity": 1
    }
  ]
}
```

Seed شامل تیتاپ و رنگارنگ، و دو فروشندهٔ شهرام و بهرامه. هر دو گزینهٔ فروش نمونه برای تیتاپ هستن. گزینهٔ فروش بالا قیمت ۱۲۵٫۵۰ و موجودی ۱ داره. گزینهٔ دوم با شناسهٔ `30000000-0000-0000-0000-000000000002`، قیمت ۱۳۰ و موجودی ۱۰ داره. اجرای موفق درخواست، سفارش واقعی ثبت می‌کنه و موجودی رو کم می‌کنه.

قیمت‌ها رو سرور می‌گیره و داخل اقلام سفارش ذخیره می‌کنه. پاسخ موفق `201` هست؛ ورودی نامعتبر `400`، گزینهٔ ناموجود `404` و کمبود موجودی `409` برمی‌گردونه. سقف تعداد اقلام، تعداد هر قلم و قیمت قابل‌فروش از تنظیمات دیتابیس خونده می‌شن.

## ثبت سفارش پشت صحنه چطور انجام می‌شه؟

پروژه دو ماژول `Catalog` و `Ordering` داره؛ هر کدوم لایه‌های Domain، Application، Contracts و Infrastructure، به‌همراه DbContext و دیتابیس مستقل خودشون رو دارن. ارتباط از طریق قراردادهای عمومی و داخل همون پردازش انجام می‌شه. هماهنگی مراحل هم با سرویس `PlaceOrder` هست.

### مراحل ثبت سفارش

1. تنظیمات فروش از دیتابیس خونده می‌شه و شناسهٔ مشتری، اقلام، تعدادها و تکراری نبودن گزینه‌های فروش بررسی می‌شن.
2. Catalog یه تراکنش باز می‌کنه و اقلام رو با ترتیب ثابت شناسه پردازش می‌کنه. برای هر قلم، موجودی با UPDATE شرطی کم می‌شه؛ فقط وقتی `StockQuantity >= quantity` باشه. قیمت روز هم داخل همین تراکنش خونده و با سقف قیمت مجاز بررسی می‌شه.
3. رسید رزرو توی `Reservations` و تعداد و قیمت اقلامش توی `ReservedStockItems` ذخیره می‌شن. کسر موجودی و ذخیرهٔ رسید با هم Commit می‌شن. اگه هر قلم مشکل داشته باشه، همهٔ این تغییرات Rollback می‌شن.
4. Ordering سفارش و اقلامش رو توی تراکنش خودش ذخیره می‌کنه. قیمت خرید از رسید میاد و مبلغ کل هم از روی همون قیمت‌ها حساب می‌شه. نتیجهٔ موفق، سفارش با وضعیت `Placed` و پاسخ `201` هست.
5. اگه ذخیرهٔ سفارش خطا بده، اول با یه DbContext تازه بررسی می‌شه که سفارش واقعاً ثبت شده یا نه. اگه ثبت نشده باشه، موجودی رزروشده برمی‌گرده و رسید آزادشده علامت می‌خوره. اگه ثبت شده باشه، همون سفارش برگردونده می‌شه و موجودی آزاد نمی‌شه.

### هم رزرو داریم، هم قفل‌گذاری دیتابیس

**رزرو** توی کد خود پروژه پیاده شده: موجودی از همون ابتدا کم می‌شه و یه رسید پایدار داریم که مشخص می‌کنه برای این خرید، از هر گزینهٔ فروش چند واحد و با چه قیمتی برداشته شده. این رسید موقع شکست سفارش، مبنای برگردوندن موجودیه. در مسیر موفق، موجودی دوباره کم نمی‌شه.

**Lock Manager** جزو خود SQL Server هست. ما Lock Manager جدا ننوشته‌ایم و برای خرید هم `lock` در C# یا دستور قفل‌گذاری دستی نذاشته‌ایم. موقع اجرای UPDATE، SQL Server خودش دسترسی درخواست‌های متعارض به همون داده رو کنترل می‌کنه. بررسی موجودی و کسرش یه دستور اتمیک هستن؛ پس دو درخواست نمی‌تونن هر دو آخرین واحد رو مصرف کنن. نوع و محدودهٔ قفل رو موتور دیتابیس انتخاب می‌کنه. [توضیح مایکروسافت دربارهٔ قفل‌گذاری](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide)

نقش این دو فرق داره: قفل‌گذاری، رقابت موقع تغییر موجودی رو کنترل می‌کنه؛ رسید رزرو، وضعیت خرید رو بعد از پایان تراکنش Catalog نگه می‌داره تا ثبت سفارش یا جبران خطا ممکن باشه. هنگام ذخیرهٔ سفارش در Ordering، تراکنش Catalog از قبل تموم شده و قفل موجودی رو برای کل فرایند باز نگه نمی‌داریم.

محدودیت CHECK هم جلوی موجودی منفی رو می‌گیره. ایندکس یکتای محصول–فروشنده برای جلوگیری از گزینهٔ فروش تکراریه و کارش با کنترل خرید همزمان فرق داره. ترتیب ثابت پردازش اقلام هم احتمال Deadlock رو کمتر می‌کنه.

### سناریوهای مهم

- **خرید عادی:** موجودی رزرو می‌شه، سفارش ثبت می‌شه و پاسخ `201` برمی‌گرده. قیمت بعدی کالا روی قیمت این سفارش اثری نداره.
- **چند خریدار برای آخرین واحد:** اگه موجودی ۱ باشه و پنج درخواست همزمان برسن، در نبود خطای دیگه، یه سفارش موفق می‌شه و چهار درخواست کمبود موجودی می‌گیرن. درخواست‌های متعارض توسط SQL Server هماهنگ می‌شن و UPDATE فقط برای موجودی کافی موفقه.
- **ورودی نامعتبر:** شناسهٔ خالی، تعداد غیرمجاز، اقلام تکراری یا عبور از سقف اقلام، با `400` رد می‌شه؛ قبل از اینکه موجودی رزرو بشه.
- **کالای ناموجود، کمبود موجودی یا قیمت بالاتر از سقف:** گزینهٔ فروش ناموجود `404` می‌گیره؛ کمبود موجودی و قیمت غیرمجاز `409`. اگه اقلام قبلی همون درخواست کم شده باشن، تراکنش Catalog همه‌شون رو برمی‌گردونه و رسیدی ثبت نمی‌شه.
- **شکست ثبت سفارش:** اگه بررسی تازه نشون بده سفارشی ثبت نشده، تعدادهای رسید به موجودی برمی‌گردن. سفارش و اقلامش هم توی یه تراکنش ذخیره می‌شن تا سفارش ناقص باقی نمونه.
- **ثبت سفارش انجام شده ولی تأیید Commit نرسیده:** بررسی تازه، سفارش موجود رو پیدا می‌کنه و همون رو برمی‌گردونه. در این حالت آزاد کردن موجودی اشتباهه، چون خرید انجام شده.
- **اجرای دوباره یا همزمان جبران:** تغییر وضعیت `Released` و افزایش موجودی توی یه تراکنش انجام می‌شن. بعد از اولین آزادسازی موفق، فراخوانی‌های بعدی موجودی رو دوباره اضافه نمی‌کنن.
- **قطع درخواست مشتری:** اگه لغو درخواست باعث خطا بعد از رزرو بشه، بررسی نتیجه و جبران با یه CancellationToken مستقل و مهلت ۳۰ ثانیه انجام می‌شن. اگه سفارش ثبت شده باشه، قطع ارتباط مشتری باعث لغو خرید نمی‌شه.
- **نامشخص بودن نتیجه یا شکست خودِ جبران:** اگه نتونیم نتیجهٔ ثبت سفارش رو بررسی کنیم، موجودی رو کورکورانه آزاد نمی‌کنیم. اگه آزادسازی هم شکست بخوره، تغییر موجودی و علامت آزادشدن با هم Rollback می‌شن. خطا و شناسهٔ رسید در لاگ Critical ثبت می‌شن و نیاز به پیگیری دارن؛ پاسخ خطای این مسیر `500` هست.
- **بن‌بست یا پایان مهلت انتظار SQL:** خطاهای شناخته‌شدهٔ این نوع، وقتی نتیجهٔ فرایند مشخص باشه، با `503` برمی‌گردن. کل خرید به‌صورت خودکار تکرار نمی‌شه؛ نتیجهٔ نامشخص یا شکست جبران، همون مسیر پیگیری بالا رو داره.

### محدودیت رزرو فعلی

این رزرو برای هماهنگی همین ثبت سفارشه؛ رزرو زمان‌دار سبد خرید یا انتظار برای پرداخت نداریم. رسید فقط وضعیت آزادشدن داره و حالت‌های جداگانهٔ «تأییدشده» و «منقضی‌شده» براش پیاده نشده. رزرو موفق با شناسهٔ رسید به سفارش وصل می‌شه. برای رزرو چنددقیقه‌ای باید زمان انقضا، تأیید یا لغو اتمیک و پردازش پس‌زمینه اضافه بشن.

بین دو دیتابیس تراکنش توزیع‌شده نداریم. خاموشی ناگهانی بعد از Commit رزرو یا قطع اتصالی که نتیجهٔ Commit رو نامشخص کنه، می‌تونه رسید بلاتکلیف باقی بذاره. بازیابی خودکار این وضعیت پیاده نشده؛ قبل از آزادسازی باید نتیجهٔ سفارش بررسی بشه. قدیمی بودن رسید به‌تنهایی دلیل آزاد کردنش نیست.

درخواست‌ها Idempotency Key هم ندارن. اگه پاسخ خرید گم بشه و POST دوباره ارسال بشه، در صورت وجود موجودی ممکنه خرید جدیدی ثبت بشه؛ این با تکرار جبران یه رسید فرق داره.

## تنظیمات فروش

جدول `CatalogDb.dbo.SalesSettings` یه ردیف تنظیمات داره: `MaxOrderItems` برای سقف اقلام، `MaxItemQuantity` برای تعداد هر قلم و `MaxUnitPrice` برای سقف قیمت قابل‌فروش. مقدار اولیه‌شون به‌ترتیب ۱۰۰، ۱۰۰٬۰۰۰ و یک میلیارد هست. تغییرشون از درخواست بعدی اعمال می‌شه و نیازی به اجرای مجدد برنامه نیست. پایین آوردن سقف قیمت، قیمت کالا رو تغییر نمی‌ده؛ خرید کالای بالاتر از سقف رو رد می‌کنه.

مثلاً برای تغییر محدودیت‌ها، این دستور رو روی `CatalogDb` اجرا کن:

```sql
UPDATE dbo.SalesSettings
SET MaxOrderItems = 50,
    MaxItemQuantity = 20,
    MaxUnitPrice = 500000000
WHERE Id = 1;
```

محدودیت‌ها باید معتبر و متناسب با ظرفیت نوع پولی دیتابیس باشن؛ اگه ترکیبشون مبلغ رو از این ظرفیت خارج کنه، ثبت سفارش تا اصلاح تنظیمات متوقف می‌شه.

## تست

```powershell
dotnet test Marketplace.sln
```

تست‌ها با SQL Server واقعی و دو دیتابیس موقت برای هر تست اجرا می‌شن. حساب اتصال باید مجوز ساخت و حذف دیتابیس داشته باشه. اتصال از `MARKETPLACE_TEST_CONNECTION`، بعد User Secrets و در نهایت اتصال ویندوز محلی خونده می‌شه. قبل از درخواست و حذف دیتابیس، نام و مالکیت دیتابیس تست بررسی می‌شه.

سناریوهای اصلی شامل خرید همزمان آخرین واحد با ۵ و ۲۰ درخواست، برگشت موجودی، شکست ذخیرهٔ اقلام، تکرار جبران، لغو درخواست، ثابت موندن قیمت خرید و استقلال ماژول‌ها هستن. تست همزمانی دقیقاً یه سفارش موفق و موجودی نهایی صفر رو بررسی می‌کنه.

برای تغییر مدل‌ها، `dotnet tool restore` رو اجرا کن و با `dotnet ef migrations add` توی پروژهٔ Infrastructure همون ماژول Migration بساز. اسکریپت SQL قابل اجرای مجدد هم با `dotnet ef migrations script --idempotent` تولید می‌شه.
